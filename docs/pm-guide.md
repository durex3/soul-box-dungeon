# 项目经理工作手册

> 写给接手项目经理工作的人（或 AI 会话）。读完本文件，再读 `docs/status.md` 和最近一个任务说明，就能接着干
> 最后更新：2026-10-30，RK-007 任务确认之后

## 1. 分工和边界
| 角色 | 由谁担任 | 做什么 | 不做什么 |
|---|---|---|---|
| 项目负责人 | 用户 | 定方向、拍板有争议的设计、试玩 | — |
| 项目经理 | 本手册的读者 | 维护 `docs/`，写任务说明，验收，合并到 `main`，更新 `docs/status.md` | 不写玩法代码、不出图、不替开发修 bug |
| 开发、测试、美术 | Codex（GPT） | 按 `AGENTS.md` 在任务分支 `rk-xxx` 上实现、写测试、用 PixelLab 出图 | 不提交到 `main`、不合并、不改 `docs/` |

- 验收发现问题时，把问题写进任务说明末尾的"验收记录"，状态改为"退回"，由 Codex 修改。项目经理不动代码
- 设计上有取舍的问题（数值、玩法规则），列出选项和各自的影响，请项目负责人选，选完再写进文档。例子：RK-004 的巨锤共鸣，负责人选了方案 B，写进了 GDD 4.8 节
- 项目负责人希望少等：长时间运行的命令先说一声在做什么

## 2. 文档地图
| 文件 | 内容 | 项目经理怎么用 |
|---|---|---|
| `docs/design-reference.md` | GDD v0.4，玩法和数值 | 任务说明引用它的章节；改动要负责人同意 |
| `docs/style-bible.md` | 美术规范 v0.2，第 13 节 PixelLab 流程，第 14 节美术验收 | 美术任务按第 14 节验收 |
| `docs/architecture.md` | 分层、编码和测试规范；第 10 节提交格式；第 11 节验收清单；第 12 节实测过的环境事实 | 每次验收逐条对第 11 节；新实测的事实补进第 12 节 |
| `docs/backlog.md` | RK-001 到 RK-119，依赖和验收标准；第 6 节开工顺序 | 按第 6 节选下一个任务 |
| `docs/status.md` | 每个任务的状态 | 只有项目经理改 |
| `docs/tasks/rk-xxx.md` | 单个任务的详细说明和验收记录 | 项目经理写，Codex 读 |
| `AGENTS.md` | 给 Codex 的规则和汇报格式 | 规则要变时改它 |
| `tools/acceptance/` | 历次验收用的脚本 | 写新任务的验收脚本时参考 |

文档冲突时的优先级：任务说明 > backlog > architecture > GDD。

## 3. 一个任务的完整流程
1. **选任务**：对照 `docs/backlog.md` 第 6 节和 `docs/status.md`，找依赖全部"通过"的任务，同一批里先做阻塞后续任务最多的
2. **先实测**：任务里要写死的参考值（期望数值、引擎行为），项目经理先在 Godot 里跑出来，必要时用 Python 独立再算一遍。实测结论写进 architecture 第 12 节。例子：`tools/acceptance/rk005_godot_ref.py`
3. **写任务说明** `docs/tasks/rk-xxx.md`，结构见第 4 节
4. **请负责人确认**任务说明，有设计取舍的先让负责人选
5. **提交并登记**：提交任务说明（`添加 RK-xxx 任务说明`），在 `docs/status.md` 里登记"待开发"
6. **Codex 开发**：负责人把任务交给 Codex，交接用的话见第 8.2 节
7. **验收**：Codex 汇报后按第 5 节验收
8. **通过**就合并（第 6 节），**退回**就写意见（第 7 节）

## 4. 任务说明的写法
参考 `docs/tasks/rk-005.md`。固定这几节：

| 节 | 写什么 |
|---|---|
| 开头表格 | 优先级 / 里程碑、依赖（写明是否已合并）、分支名 |
| 目标 | 一两段：做什么、依据哪节文档、后面哪些任务会用到它；明确本任务不做到哪一步 |
| 要做的 | 文件路径、类名、公开接口的签名；算法要"照做"的写清每一步；给出项目经理实测过的参考值 |
| 测试 | 必须有的用例逐条列出，要求汇报时按顺序对应 |
| 不要做的 | 容易顺手做掉的后续任务内容；不许改的目录（通常是 `docs/`、`game/project.godot`、`game/data/`） |
| 自检步骤 | 开发自己跑的步骤，至少包括一次故意改坏、确认测试会失败、再改回 |
| 验收标准（backlog） | 原样抄 backlog 那一行 |
| 验收方式预告 | 写明项目经理会重做哪些自检、会另外试什么，例如"再写几种说明里没列出的违规写法" |
| 验收记录 | 写"（暂无）"，验收后填 |

写法要求：
- 能写成数字、文件路径、命令的，不写成描述
- 规则变严时（例如 RK-005 把 `rng.randomize()` 从合法移到违规），在说明里写明"这是收紧检查，不算放宽测试"，免得 Codex 以为违反了 AGENTS.md 的禁止条款
- 例外条件写清按什么判断（例如"按文件路径，不按 `class_name`"）

## 5. 验收
### 5.1 准备
在单独的工作树里验收，不动负责人的工作区：

```bash
git worktree add --detach /tmp/sbd-rk0xx rk-0xx
cd /tmp/sbd-rk0xx && python3 tools/run_tests.py   # 退出码 0，最后一行 TESTS: N passed, 0 failed
```

### 5.2 检查内容
1. `docs/architecture.md` 第 11 节的 7 条逐条过一遍，任何一条不满足就退回
2. backlog 里的每条验收标准都要有对应的测试或检查，并且结果符合
3. 重做任务说明里的自检步骤，特别是"故意改坏"那几步，确认测试真的会失败
4. 自己另找几个说明里没列的情况试一试：没列过的种子、没列过的违规写法、没列过的坏数据。历次的做法见 `tools/acceptance/`：

| 脚本 | 验收内容 |
|---|---|
| `rk003_probe.sh` | 断言失败、运行时报错、死循环超时、解析错误、模拟层违规，看测试运行器能不能报出来 |
| `rk004_verify.py`、`rk004_probe.gd` | 改坏数据表，看校验能否拦下 |
| `rk005_verify.py` | 用 Python 参考实现核对派生结果；改常量、加违规写法，看测试和分层检查能否拦下 |
| `rk005_godot_ref.py`、`rk005_godot_probe.gd` | 写任务说明前的实测：Godot 和 Python 算同一组数，比对 |

5. 读改动：`git diff main...rk-0xx --stat`，确认只改了本任务范围内的文件，提交说明符合 architecture 第 10 节
6. 临时改动全部还原，`git status --short` 干净，然后 `git worktree remove /tmp/sbd-rk0xx`

### 5.3 怎么判
- 任务说明要求的都满足 → 通过
- 发现的问题不在本任务说明的范围内（例如 RK-005 验收时发现 RK-003 留下的检查漏洞）→ 本任务照常通过，问题写进验收记录的"遗留"一节，另开任务
- 画面相关的验收标准才截图，其余用命令输出或 Godot MCP 的运行输出判断。像素分析可以用 Pillow

## 6. 通过时
```bash
git switch main
git merge --no-ff rk-0xx -m "合并 RK-0xx: <任务名>"
python3 tools/run_tests.py      # 在 main 上再跑一次，必须通过
git branch -d rk-0xx
```
然后：
1. `docs/status.md`：状态改"通过"，说明栏写"<一句话>，提交 <Codex 的提交>，合并 <合并提交>"
2. `docs/tasks/rk-0xx.md` 的验收记录：写"### <日期> 通过（提交 …，合并 …）"，下面逐条列出自检和额外检查的结果；有遗留的单独写一节
3. 一起提交：`文档: RK-0xx 验收通过`

## 7. 退回时
1. 在 `docs/tasks/rk-0xx.md` 的验收记录里写"### <日期> 退回"，每条问题写清：
   - 对应 architecture 第 11 节的第几条，或任务说明的哪一节
   - 怎么复现（命令和输出）
   - 要改成什么样
2. `docs/status.md` 改为"退回"，提交 `文档: RK-0xx 退回`
3. 告诉负责人，让 Codex 按 AGENTS.md 里退回的流程改（切回原分支、合入 `main`、逐条改）

## 8. 交接用的话
### 8.1 给新项目经理的开场
接手时把下面这段发给新的项目经理（人或 AI 会话）：

```
你是《魂匣地牢》的项目经理。仓库在 ~/Desktop/soul-box-dungeon（Godot 4.7.2 单机像素肉鸽）。
先读 docs/pm-guide.md，再读 docs/status.md 和最新的 docs/tasks/rk-xxx.md，然后告诉我：
1. 当前进度：哪些任务通过了，有没有待验收或退回的
2. 下一个该做的任务（按 backlog 第 6 节）和理由
分工：我是项目负责人，拍板设计问题；你写任务说明、验收、合并、维护 docs/；Codex（GPT）负责开发、测试和美术。
你不改代码。验收发现问题就写进验收记录、状态改为退回，让 Codex 修。
验收默认看命令输出和 Godot MCP 的运行输出，需要看画面时才截图。
```

### 8.2 给 Codex 的话
新任务：
```
做 RK-0xx。先读 AGENTS.md 和 docs/tasks/rk-0xx.md，按里面的流程做，做完按 AGENTS.md 的汇报格式回复。
```
退回后：
```
RK-0xx 被退回，意见在 docs/tasks/rk-0xx.md 末尾的验收记录里。按 AGENTS.md 里退回任务的流程改，汇报时逐条说明怎么改的。
```

## 9. 环境
| 项 | 内容 |
|---|---|
| Godot | `/Applications/Godot.app/Contents/MacOS/Godot`（4.7.2），或环境变量 `GODOT_BIN` |
| 跑 Godot | 一律用 Python `subprocess.run(..., timeout=...)`，脚本出错时 Godot 可能不退出；macOS 没有 `timeout` 命令。新工作树先 `--headless --path game --import` |
| Python | 3.9；工具只用标准库，项目经理验收可以用 Pillow 11.3.0 |
| Godot MCP | `@coding-solo/godot-mcp@0.1.1`，按项目配在本机。换电脑重新装：`claude mcp add godot -e GODOT_PATH=/Applications/Godot.app/Contents/MacOS/Godot -- npx -y @coding-solo/godot-mcp@0.1.1` |
| 版本库 | 只有本地 git，远程托管以后再定 |
| PixelLab | 负责人已付费，确认可以商用（style-bible 13.4 节）。令牌只放环境变量 |
